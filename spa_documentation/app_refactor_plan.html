The mirror contract

A test file changes for the same reason as its source file. Test naming makes that relationship mechanical and reviewable.

app/<path>/<name>.ts └── app_tests/<path>/<name>.test.ts one focused test-design stub app/tsconfig.json └── app_tests/tsconfig.json inherits the same strict rules Mirrored feature boundaries ├── catalog/ pure tree, path, and tab data ├── core/ wire contracts, decoding, HTTP, clipboard, API ├── nav/ state, presentation model, presenter, DOM view ├── routing/ hash policy and browser adapter ├── content/ source, sink, Decorator, coordinator │ └── enhancers/ one handler concern per file ├── tabs/ Strategy contract, registry, three activations ├── mermaid/ runtime, load, render, and interactions ├── construction/ task read/traverse/status/trail/nav/build/import ├── update/ cache, refresh, lifecycle, view, Mediator ├── testing/ stable browser seam only ├── composition-root.ts concrete assembly and lifecycle ├── config.ts runtime values only └── main.ts entry-point seam only

SRP gate: unit tests for another module do not belong in the nearest convenient file. Cross-module lifecycle evidence belongs with the owning coordinator, the composition root, or a deliberate browser-integration entry point.

Pattern boundaries

Patterns are admitted only where a real variation, lifecycle, or integration boundary exists.

The composition root is not an Abstract Factory. The discriminated update lifecycle is not a GoF State hierarchy. The generic action binder is not Template Method. No Singleton, event bus, service locator, or speculative helper layer belongs in this refactor.

Migration work order

The skeleton supports review; it does not skip any implementation step. Each numbered step remains one coherent, green commit.

  1. Toolchain and characterization safety net current

    The repository-local compiler, package lock, build and browser-test runners, generated-output policy, start.sh hook, and first six characterization tests are complete. Update lifecycle cases and compiled TypeScript unit assertions remain.

  2. Pure catalog and routing policies waiting

    Implement catalog literals, tree traversal, document paths, tab descriptors, and pure hash parsing.

  3. HTTP Adapter, decoders, and DocsApi Facade waiting

    Make the fetch adapter the sole raw-I/O boundary and decode all untrusted JSON from unknown.

  4. Mermaid Strategies and enhancer chain waiting

    Guarantee scripts → diagrams → run-tests → terminal after every successful insertion.

  5. Navigation Observer, Presenter, and passive view waiting

    Give main navigation one state owner and remove state and catalog reads from the DOM view.

  6. Content controller and tab Strategies waiting

    Remove tab-key branching from controllers and route every insertion through the decorated host.

  7. Construction Status subsystem waiting

    Implement task reading, traversal, status, trail, navigation, lesson building, canonical import, and summary in dependency order.

  8. Update Documentation subsystem waiting

    Implement the status cache, refresh use case, finite-state lifecycle, passive view, and Mediator.

  9. Composition root and browser cutover waiting

    Wire, expose window.__spa, load generated ESM, verify the proxy, then remove legacy app.js.

Current checks and hard gates

  • Type-check app/tsconfig.json and app_tests/tsconfig.json independently.
  • A test stub is never counted as an executable test or passing assertion.
  • Only fetch-http-client.ts may call raw fetch().
  • Views receive models and callbacks; they do not fetch, traverse domain trees, or read global state.
  • Every HTML insertion passes through EnhancedContentHost.
  • All API and Mermaid URLs remain relative for the /agent-block/ reverse proxy.
  • Before cutover, verify revalidation for every emitted ESM submodule; versioning only the entry is insufficient.
  • The live app.js and its cache stamp remain untouched until the final verified cutover.
