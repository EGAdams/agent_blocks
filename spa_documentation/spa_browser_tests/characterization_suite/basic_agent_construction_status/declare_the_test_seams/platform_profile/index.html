Three decisions carry it. ServerSpawnPlan is data describing a launch rather than a launch, so the module that spawns the child process never learns which host it is on. Every member is readonly and every array is ReadonlyArray, so a profile cannot be mutated by the code it is handed to. And createWindowFocuser() returns a product rather than a boolean, which is what keeps “this host cannot raise a window” expressible as a Null Object instead of an if.

These pages call a file like this a plug-in point — an opening with a written-down shape, so different components can be plugged in later without the surrounding code noticing. Here it is the Gang of Four Abstract Factory: one interface handing out a whole family of related products that have to agree with each other.

On Linux both processes are already on the same side of the boundary, so the plan collapses to python3 server.py <port> with a real cwd, and the window focuser becomes the Null Object. The difference between the two files is exactly the difference between the two hosts, and nothing else in the suite has to know about it.

Why this is not two if-statements Every host difference is one profile. A run either has the Windows family or the Linux family — it can never end up with the WSL spawn plan and the Linux Chrome path, which is precisely the mismatch a scattered isWindows check produces.

5. One run through it

Figure 1 is the arrangement; this is the motion. Every host-specific decision in a whole test run is made in the first three messages and never revisited.

  1. The test runner asks the composition root to assemble one whole environment; this is the only entry point a test file imports.
  2. The composition root asks TestConfig to read the run's configuration from process.platform and process.env.
  3. TestConfig returns an immutable configuration object, so every module below this point is testable with a hand-built config.
  4. The composition root selects one concrete profile. This is the single line in the suite that names a host.
  5. SpaServer is constructed against the interface; it never learns whether it holds the Windows or the Linux family.
  6. BrowserSession is constructed the same way, and it is the only module that imports Playwright's launcher.
  7. SpaServer asks the profile how to launch server.py on the reserved port, instead of deciding for itself.
  8. The profile answers with a plain ServerSpawnPlan: a command, its arguments, and a working directory or null.
  9. SpaServer spawns that plan and polls index.html until the child process answers, then hands back a base URL.
  10. BrowserSession asks the same profile for the host's Chrome binary and the flags it needs.
  11. The profile answers with the executable path and launch arguments belonging to this host's family.
  12. The browser is launched and the six characterization tests can begin, with no host check left anywhere in the run.

Figure 2. Steps 7–11 are the whole point: two different consumers ask the same object two different questions, and each gets an answer from the same host's family.

  • Step 4 is the point of the whole file. One line chooses a host. Delete it and the suite still compiles — it just has nothing to run against.
  • Steps 8 and 11 are the seam. Data comes back, not behavior. Neither consumer executes anything the profile chose; they act on a value.

6. How to check this yourself

  1. cat browser_tests/platform-profile/platform-profile.ts — 21 lines, one interface, four products.
  2. grep -rn "isWindows" browser_tests/ — two hits, both inside composition-root.ts and test-config.ts. A third hit means a host check has leaked back out into a consumer.
  3. grep -n "page.locator\|getByRole" browser_tests/*.test.ts — no hits. The tests speak SpaPage, never a raw selector.
  4. npm run typecheck — passes across all three projects.
  5. npm test — 6/6 pass on a host whose Chrome is where the profile says it is.

7. What has to happen next

  1. Make the Chrome path discoverable — the item in progress. CHROME_PATH is a module-level const in both profiles with no environment override. On a machine whose Chrome is anywhere else — a Playwright-managed download, a distro package, a different Windows install — npm test fails at launch with executable doesn't exist and the only fix is editing a source file. A SPA_TEST_CHROME variable read in readTestConfig() would fit the existing shape exactly, since every other environment input already arrives that way.
  2. Decide whether a missing browser is a skip or a failure. Today it is six failures that look like broken tests rather than a missing prerequisite. That is a reporting decision, not a typing one.
  3. Add a third profile. The “adding a host means adding a profile” claim in the file's own doc comment has never been exercised. A macOS profile would either confirm it or reveal a product the interface is missing.
  4. Cover the profiles with unit tests. serverSpawnPlan() is a pure function from a port to a plan — the cheapest thing in the suite to test, and currently untested in either implementation.
