Three decisions carry it. withSpaPage() makes every test end the same way — acknowledge the step, release the page — so a failing assertion can never leak a browser page into the next test. The environment is created once at module scope and started in before(), so six tests share one server and one browser rather than paying that cost six times. And concurrency: false is deliberate: these tests share one SPA instance, and the run is a demonstration a human can watch in headed mode.

Every line in the test file speaks the vocabulary of the SPA — openHome, clickLink, expectNav, loadDetailTab. That is the Page Object pattern, and it is what makes these tests readable as a description of the product rather than as browser automation.

3. What the six tests actually pin

Each row is one test(). Together they are the definition of “the rewrite did not change anything”.

#The testWhat would break it
1Renders the established home navigation in orderAdding, removing, renaming or reordering a top-level section.
2Drills to a leaf and preserves all five detail tabsA detail tab that 404s, renders empty, or loses its active state — plus the Update Documentation bar failing to appear.
3Applies a deep-linked tab and scrolls to its anchorThe #item=…&tab=…&anchor=… route format changing, or the anchor scroll being dropped.
4Falls back to Home for an unknown deep linkAn invalid route throwing, or rendering a blank page instead of Home.
5Hides the in-page header in embedded mode?embedded=1 no longer setting body.embedded, or the dashboard iframe regaining a duplicate nav.
6Drills into both embedded lessons and backs out one level at a timeA canonical lesson failing to load, its two Mermaid figures failing to render, either terminal button failing to wire, or Back skipping a level.
Test 6 is the load-bearing one It asserts svg count is exactly 2 and that both buttons carry their wired flag. That single test covers the canonical-lesson fetch, URL rebasing, Mermaid rendering, and button wiring — the four things that silently produce a blank panel rather than an error.

  1. The author adds a new top-level section to app.js's sections object and runs the suite.
  2. The test file asks the environment to start; this happens once in before(), not per test.
  3. The environment reserves an ephemeral port and spawns server.py, then polls until it answers.
  4. server.py answers 200 on index.html, and the environment hands back the base URL for this run.
  5. The first test opens the SPA home page through the page object.
  6. The page object asks the navigation probe to compare the rendered nav against the fixture.
  7. The comparison fails: the fixture lists six sections and the page renders seven, so the two tests that assert the home navigation fail while the other four stay green.
  8. The author updates the fixture, placing the new label where the nav actually renders it.
  9. The author runs the suite again with no other change.
  10. The first test opens home again, against the same unchanged app.js.
  11. The probe compares the rendered nav against the corrected fixture.
  12. All six tests pass in about eight seconds; the change is now recorded as intended, not accidental.
  13. The environment stops, closing the browser and terminating the server child process.

Figure 2. This is what a characterization suite is for: the nav change was intended, and the suite still made it impossible to make silently.

  • Steps 7–8 are the alarm. Four tests stayed green, so the failure named the change precisely instead of collapsing the whole run.
  • Step 9 is the decision. Updating a fixture is how an intentional change is recorded. If nobody can say why the fixture changed, the change was not intentional.

6. How to check this yourself

  1. cat browser_tests/legacy-navigation.test.ts — 141 lines, six test() calls.
  2. grep -rn "createWindowsPlatformProfile\|createDialogStepGate" browser_tests/ — hits only in composition-root.ts and each module's own file. Anything else means an implementation choice leaked out of the composition root.
  3. grep -n "page.locator\|getByRole" browser_tests/*.test.ts — no hits. A hit means a raw selector escaped the page object.
  4. npm run typecheck — passes across app/, app_tests/ and browser_tests/.
  5. npm test — tests 6 / pass 6 / fail 0. Needs Chrome where the platform profile expects it.

The button opens a Windows Terminal tab on the Ubuntu-26.04 profile, runs all five checks in order, and then leaves the shell open so the output can be read and the workspace kept. npm test takes about eight seconds; the whole run is under a minute.
