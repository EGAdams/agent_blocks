Live Plan

Building the Characterization Suite

Five stages, nineteen checkable items, and a safety net that is already green before the rewrite starts

1. The one sentence version

Where we are Stages 1 through 4 are finished: twenty-two typed modules and six characterization tests pin down what the legacy app.js does today, and they pass in about eight seconds. We are inside Stage 5, where the first item is that the suite cannot start on a host whose Chrome is not at a hard-coded path. Nothing under app/ is loaded by the browser yet, and no part of the rewrite has been cut over.

2. What the three status words mean

  • Done — the file is on disk, it compiles under strict TypeScript, and something you can run exercises it. Not “designed”.
  • In progress — started, and the thing blocking it is named on its own page.
  • Not started — deliberately cold, because something above it would make the work be done twice.

3. The verified fact base

  • browser_tests/ holds 21 modules plus one test file, 1,203 lines in total, one directory per module.
  • npm run typecheck passes across all three projects — app/ (62 design modules), app_tests/ (the mirrored stubs), and browser_tests/.
  • npm test reports tests 6 / pass 6 / fail 0 in roughly 8.0 seconds, driving a real Chrome against a real server.py on an ephemeral port.
  • The suite already caught one real change: adding this section to the SPA nav failed two of the six tests until nav-fixtures.ts was updated to match.
  • app_tests/ mirrors all 62 app/ modules as .test.ts files that contain no executable assertions. It is a review guide, not coverage — the only executable tests in this repo are the six in browser_tests/.
  • CHROME_PATH is a module-level const in both platform profiles, with no environment override. On a host without Chrome at that exact path, all six tests fail at browser launch.

7. How to read the rest of this plan

Open a stage in the sidebar to see only its items; open an item to see only that item. A row with a red corner triangle has children. Two items — Platform Profile and Characterization Suite — carry full lessons whose source of truth is their own leaf file, not this page.

  1. Stage 1 — Declare the test seams Turn every host and headed/headless difference into an object the rest of the suite can hold without inspecting. Done

    What this stage actually means

    A test suite that runs on two hosts will grow host checks everywhere unless somebody decides, early, where those differences are allowed to live. This stage makes that decision: one abstract factory for the host family, and Null Objects for everything that only happens when a human is watching.

    This stage is finished. That is a real milestone and also a modest one: a declared seam proves the differences are expressible, not that the suite starts anywhere.

    What was built

    Five artifacts: the PlatformProfile interface with its two implementations, the StepGate / HoldOpenNotice / WindowFocuser ports with a Null Object each, and the fixtures module that holds the expected navigation as plain data.

    How to check this yourself

    grep -rn "isWindows" browser_tests/ returns two hits, in test-config.ts and composition-root.ts. A third hit means a host check has leaked into a consumer, which is exactly what this stage exists to prevent.

    What this unlocked

    Stage 3 — a run can now be assembled from one call, because the only thing that varies between hosts arrives as a constructor argument rather than as a branch inside each module.

    1. Write the platform profile One abstract factory supplying the spawn plan, the browser path, its flags, and a window focuser. Done
    2. Give every headed-only behaviour a Null Object StepGate, HoldOpenNotice and WindowFocuser, so a headless run has nothing to check. Done

      What this item actually means

      Three things happen only when a human is watching a headed run: the browser window is raised, a Windows 95 style dialog waits for a click between steps, and a banner holds the final page open. The obvious implementation is an if ( showBrowser ) at each of the three call sites. This item is the decision not to do that.

      Each one is a port with two implementations: the real one and a Null Object whose method body is a comment. A headless run gets the Null Objects and never asks whether it is headless.

      What was built

      step-gate.ts, hold-open-notice.ts and window-focuser.ts each declare an interface and export a createNull* factory in the same file. The real implementations live separately, in dialog-step-gate/, banner-hold-open-notice/ and powershell-window-focuser/, and are named only by the composition root.

      HoldOpenNotice.present() takes openPage: () => Promise<Page> rather than a page, so a run that holds nothing open never pays for opening one. That is the detail that keeps the Null Object genuinely free.

      How to check this yourself

      grep -rn "showBrowser" browser_tests/ — hits in test-config.ts, composition-root.ts and browser-session.ts only. No test and no page-object method asks whether the run is headed.

      Where the coverage stops

      The Null Objects are exercised on every headless run. The real implementations are exercised only when somebody runs npm run test:headed on Windows, which nothing automated does. A PowerShell change or a Chrome window-title change would not be caught by npm test.

    3. Hold the expected navigation as data One module, no imports, listing exactly what app.js is expected to render. Done

      What this item actually means

      nav-fixtures.ts is 55 lines with no import statement at all. It knows nothing about Playwright, Node, or the DOM. It is the written-down answer to “what should the SPA show?”, kept separate from every mechanism that goes and looks.

      That separation is what makes an intentional change cheap and an accidental one loud. Renaming a section is a two-line diff here plus a green run; renaming one by accident is two failing tests.

      What was built

      HOME_NAV_LABELS and DETAIL_NAV_LABELS as ordered arrays, DETAIL_TABS pairing each tab label with the file it fetches, EMBEDDED_LESSONS naming the two canonical lessons, and the deep-link hashes including the deliberately invalid one used by test 4.

      How to check this yourself

      grep -c import browser_tests/nav-fixtures/nav-fixtures.ts returns 0. If it ever returns more, expected values and the machinery that checks them have started to mix.

      What this unlocked

      Every assertion in the suite that says “this is what the SPA looks like” points at one file, so the answer to “was that change intended?” is always a diff of this module.

  2. Stage 2 — Speak SPA, not selectors Give the tests a vocabulary of the product, so a markup change touches one file instead of six tests. Done

    What this stage actually means

    A browser test that names #nav a.active is coupled to markup, not to behavior, and it has to be rewritten every time the markup moves — which is precisely what a rewrite does. This stage puts a Page Object between the two so the tests survive the thing they exist to protect.

    What was built

    SpaPage, an interface of twelve product-shaped operations, and NavigationProbe, the only module that names the #nav selector.

    How to check this yourself

    grep -n "page.locator\|getByRole" browser_tests/*.test.ts returns nothing. Every selector in the suite lives in spa-page.ts or nav-probe.ts.

    What this unlocked

    The six tests read as a description of the SPA, which is what makes them usable as the specification the rewrite has to satisfy.

    1. Write the SpaPage page object openHome, clickLink, expectNav, loadDetailTab — the SPA's vocabulary, not Playwright's. Done

      What this item actually means

      One interface of twelve operations, each named after something a person does to the documentation site. A test says await spa.clickLink( "Basic Agent" ); it does not say which element that is or how the click is dispatched.

      What was built

      createSpaPage() takes a Playwright Page, a base URL, a NavigationProbe and a StepGate, and returns the interface. The most interesting method is loadDetailTab(): it registers a response listener before clicking, so the HTTP status of the fetched partial can be asserted without a race.

      How to check this yourself

      grep -n "#content" browser_tests/ -r — one file. grep -n "#nav" browser_tests/ -r — one file, and a different one.

      Where the coverage stops

      SpaPage has no method for the Update Documentation controls, which is the mechanical reason queue row 2 has not been written yet: the vocabulary for it does not exist.

    2. Isolate every #nav assertion One module owns the nav selector and the wait-then-assert pattern that makes it stable. Done

      What this item actually means

      The SPA replaces its whole nav on every drill-down, so reading the labels immediately after a click is a race. NavigationProbe owns the fix: waitForFunction until the rendered labels match, then a real assertion so a timeout still reports a readable diff.

      What was built

      Three methods — labels(), expectLabels(), expectActive() — and two selector constants. Forty lines.

      How to check this yourself

      Delete the waitForFunction and run the suite: the drill-down tests become flaky rather than failing outright, which is the failure mode this module exists to remove.

  3. Stage 3 — Assemble one run One call starts a server and a browser; one module decides every implementation. Done

    What this stage actually means

    Test files should not know that a run needs a free port, a child process, a readiness poll and a browser launch. This stage hides all four behind createLegacyNavigationEnvironment() and puts every concrete choice in one file.

    What was built

    SpaServer over port reservation and readiness polling, BrowserSession over Playwright's launcher, TestEnvironment as the facade over both, and the composition root that wires them.

    How to check this yourself

    The test file imports exactly one factory. grep -n "^import" browser_tests/legacy-navigation.test.ts shows Node's test API, the composition root, the fixtures, and one type — no Playwright, no child process.

    What this unlocked

    Stage 4 — the tests could be written as behavior descriptions, because none of the setup appears in them.

    1. Start server.py on a port nobody is using Reserve an ephemeral port, spawn the profile's plan, poll until index.html answers. Done

      What this item actually means

      Three small collaborators rather than one function: PortReservation binds port 0 and reads back what the kernel gave it, ServerReadiness polls a URL on a schedule, and SpaServer uses both plus a PlatformProfile to produce a base URL.

      Splitting them is what keeps SpaServer free of both node:net and a retry loop, and it is why the fixed port 8931 the developer uses never collides with a test run.

      What was built

      createEphemeralPortReservation(), createHttpPollingReadiness({ attempts: 50, intervalMs: 100 }) — a five-second ceiling — and createSpaServer(), which spawns with stdio: "ignore" and kills with SIGTERM.

      Where the coverage stops

      Nothing tests the readiness timeout path. If server.py failed to start, the suite would report a readiness error five seconds later rather than the actual Python traceback, which is stitched to /dev/null by stdio: "ignore".

    2. Own the browser lifecycle in one place The only module that imports Playwright's launcher, and the only one that knows about instrumented pages. Done

      What this item actually means

      A page and the thing that must be torn down to release it are not always the same object: a plain page is closed, an instrumented page owns a whole browser context that has to be closed instead. ManagedPage pairs each page with its own dispose() so callers never have to know which kind they hold.

      What was built

      createBrowserSession() with open(), newPage(), newInstrumentedPage( initScript ) and close(). The headed-only window position and size flags are appended here; the executable path and base flags come from the platform profile.

      How to check this yourself

      grep -rn "from \"playwright-core\"" browser_tests/ — the launcher is imported once, here. Two other modules import only types from it, which vanish at compile time.

    3. Reduce a whole run to start, newPage and stop Pages arrive already wrapped as SpaPage objects, with the base URL and probe attached. Done

      What this item actually means

      TestEnvironment is the seam between “a suite of tests” and “a server plus a browser”. It holds the base URL as private state, refuses to hand out a page before start() with a named error, and wraps every raw page into an SpaPage on the way out.

      What was built

      Four methods over five injected collaborators. stop() runs the hold-open notice first, then closes the browser, then the server — the order matters, since the notice needs a live page to draw its banner on.

      How to check this yourself

      Call newPage() before start() and the failure is The test environment is not started. rather than an undefined-property crash three frames deeper.

    4. Name every concrete implementation exactly once Four small select* functions, and the only file in the suite allowed to choose. Done

      What this item actually means

      Every question of the form “which implementation?” is answered in this one 68-line file: which platform profile, whether the window focuser is real, whether the step gate pauses, whether the hold-open notice draws a banner. Each is one named function of two lines, so the whole policy can be read at once.

      What was built

      selectPlatformProfile, selectWindowFocuser, selectStepGate and selectHoldOpenNotice, then createLegacyNavigationEnvironment() which assembles them. Note selectHoldOpenNotice's two conditions: headed and a non-zero hold, so SPA_TEST_HOLD_OPEN_MS=0 degrades to the Null Object rather than to a zero-length wait.

      How to check this yourself

      grep -rln "createDialogStepGate\|createBannerHoldOpenNotice" browser_tests/ — each name appears in its own module and in the composition root, nowhere else. This is check 2 of the Characterization Suite lesson's section 6.

  4. Stage 4 — Characterize the legacy SPA Write down what app.js does today, in tests, before anything replaces it. Done

    What this stage actually means

    A characterization test does not assert what the code should do. It asserts what the code does, so that a rewrite which changes behavior has to say so out loud. This stage is the safety net the whole TypeScript migration is supposed to fall into.

    What was built

    Six tests in one file covering home navigation, all five detail tabs, deep links with anchors, invalid-route fallback, embedded mode, and both canonical lessons including their Mermaid figures and terminal buttons. Plus the headed presentation that lets a person watch the same run.

    How to check this yourself

    npm test — tests 6 / pass 6 / fail 0, about 8.0 seconds.

    What this unlocked

    Permission to start changing app.js. Before this stage, every edit to a 1,301-line file was unverifiable by anything except opening the browser and remembering what it used to do.

    1. Write the six characterization tests Nav, detail tabs, deep links, invalid routes, embedded mode, and both canonical lessons. Done
    2. Let a person watch the same run A Windows 95 style OK dialog between steps, and a banner that holds the last page open. Done

      What this item actually means

      npm run test:headed runs the identical six tests through Windows Node and native Windows Chrome, so the browser appears on the desktop rather than inside WSLg. Between steps a dialog waits for a click; at the end a banner holds the result page for ten seconds.

      None of that is an if inside a test. It is the same six tests with different objects injected.

      What was built

      dialog-builder.ts — at 193 lines the largest module in the suite — is a Builder that is serialized and evaluated inside the page. That constraint shapes it: it closes over nothing but its spec argument, and every part is built by its own local function. dialog-step-gate.ts then waits on the click flag with timeout: 0, so the watcher sets the pace.

      How to check this yourself

      On Windows: npm run test:headed. The WSLENV assignment in package.json is what carries the three SPA_TEST_* variables across the WSL boundary; without it the run would silently fall back to headless.

      Where the coverage stops

      Nothing automated runs this path. It is verified by a person watching it, which is appropriate for a presentation feature and worth stating plainly rather than implying the six green tests cover it.

  5. Stage 5 — Extend the safety net Make the suite startable anywhere, then cover the part of app.js it still leaves unpinned. In progress

    What this stage actually means

    Six green tests are a real safety net and a narrow one. This stage asks two questions: can somebody else run it, and does it cover enough of app.js for a red run after cutover to mean something specific?

    What exists today

    The gap is measured, not guessed. The suite runs and passes; it fails at browser launch on a host whose Chrome is elsewhere, and it asserts nothing about the Update Documentation lifecycle beyond that its tab returns 200.

    What is still missing

    An environment override for the browser path, a test that drives the Update button, and the first app_tests/ stub converted into a real assertion.

    How we will know this stage is done

    npm test passes on a machine nobody configured by hand, and the Update Documentation lifecycle fails the suite when it breaks.

    1. Make the Chrome path discoverable Read SPA_TEST_CHROME in readTestConfig(); fall back to today's constant. In progress

      What this item actually means

      CHROME_PATH is a module-level const in both platform profiles — /usr/bin/google-chrome on Linux, the Program Files path on Windows. There is no environment override, so on a host whose Chrome is anywhere else the only way to run the suite is to edit a source file.

      What exists today

      The failure is precise and reproducible: browserType.launch: Failed to launch chromium because executable doesn't exist at /usr/bin/google-chrome, reported as six failed tests rather than as a missing prerequisite. Pointing the compiled profile at a Playwright-managed Chromium instead makes all six pass unchanged, which is what confirms the path is the whole problem.

      What is still missing

      One field on TestConfig, one env[ "SPA_TEST_CHROME" ] ?? in readTestConfig(), and both profiles returning it. Every other environment input in this suite already arrives exactly that way, so the shape is settled — only the typing is left.

      How we will know it is done

      SPA_TEST_CHROME=/path/to/chrome npm test passes on a machine with no Chrome at the default location, and plain npm test keeps working where there is one.

      The next concrete action

      Add readonly chromePath: string to TestConfig, populate it in readTestConfig(), and have both profiles return config.chromePath from browserExecutablePath().

    2. Characterize the Update Documentation lifecycle The git-status badge, the Update button, and the polling loop behind it. Not started

      What this item actually means

      Test 2 opens the Update Documentation tab and asserts it returns 200 with non-empty content. Everything the tab then does — fetching api/git-status, rendering a dirty/clean badge, starting a run, polling api/run-update-status, reloading the report — is unasserted. It is the largest single behavior in app.js with no baseline.

      What is still missing

      An SpaPage vocabulary for those controls, which does not exist yet, and a decision about the real Claude Agent SDK subprocess: a characterization test must not start a billed agent run, so the update route needs to be observed rather than driven, or driven against a leaf whose run is stubbed.

      Why it is not started

      Queue row 1 comes first. Writing tests that can only be run on one pre-configured machine is how a safety net quietly becomes one person's private tooling.

    3. Turn one app_tests directory into real assertions 62 mirrored stubs currently contain no executable test; make one directory real. Not started

      What this item actually means

      app_tests/ mirrors all 62 app/**/*.ts modules as <name>.test.ts. Each one names a single test responsibility and its planned evidence, and none contains an assertion. The mirror type-checks, which is easy to mistake for coverage; it is a review guide.

      What is still missing

      A compiled unit-test slice with the same treatment browser_tests/ already has — its own emitting tsconfig.json, an npm script, and output under dist/. Then one directory of stubs becomes real tests.

      Why it is not started

      Pure policies and parsers are the right first slice, and most of them do not exist yet as implementations — app/ is still a design skeleton. Writing assertions against declarations would produce tests that pass without executing anything.
