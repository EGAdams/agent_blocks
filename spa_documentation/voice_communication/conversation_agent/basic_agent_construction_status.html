Words like “done” drift over time, so on this plan each status word is tied to something you can go and look at: a file that is on disk, a command you can run, or a screen you can watch. Every item names its own. If you cannot open the thing it names, the status has not been earned yet.

  1. Stage 1 — Declare the plug-in point Give the boundary between voice policy and any agent backend a name, a file, and a typed shape. Done

    What this stage actually means

    A plug-in point is a promise written in the type system: whatever answers our questions must look like this. Declaring it is cheap and it is not the same as building anything. Its whole value is that the code above the boundary — voice policy, the Toyota screen — can now be written against a name instead of against a particular vendor's SDK.

    This stage is finished. That is a real milestone and also a modest one: a declared plug-in point proves the design is expressible, not that it works.

    What was built

    Three artifacts, all type-only: the interface itself, the shared event vocabulary it streams, and the barrel file that publishes both to consumers.

    How to check this yourself

    From voice_communication/, run npm run typecheck. It runs tsc -p tsconfig.json and currently exits clean. If a later edit makes the contract inconsistent with its consumers, this is the check that catches it first.

    What this unlocked

    Stage 2 — someone can now try to implement the plug-in point and find out whether the shape survives contact with a real agent SDK.

    1. Write the interface file One operation, submit( text, generation ), returning an async stream of AgentEvent. Done
    2. Define the shared event contracts AgentEvent, its five kinds, and the SessionId / GenerationId aliases the whole boundary shares. Done

      What this item is protecting against

      Suppose Toyota imports ../../voice_communication/conversation_agent/conversation_agent.js. That one line quietly turns two private facts into public API: that a folder is named conversation_agent, and that it sits exactly two directories up. Rename the folder, split it, or move the package, and the import breaks — not because the interface changed, but because the furniture moved.

      A barrel fixes the public surface at one path. Behind it, folders may be renamed, merged, or split, and the repair is one line inside the barrel instead of one line inside every consumer. That is the whole trade: one file absorbs the churn so the other files do not have to.

  2. Stage 2 — Prove the plug-in point with one working adapter Find out whether anything can really implement submit() before betting four more blocks on the shape. In progress

    What this stage actually means

    A plug-in point that has never been implemented is a guess. This stage cashes the guess by building one adapter against a real agent SDK and letting the friction show up while it is still cheap to change the interface.

    It half worked, in the most useful way. The adapter exists, streams, and is tested — and building it exposed a disagreement about the event shape that a diagram would never have revealed. That disagreement is now the item in progress.

    What exists today

    The reference implementation is claude_agent_adapter/ in the parent workspace: a Python Protocol mirroring IConversationAgent, an adapter wrapping claude-agent-sdk's query(), and an offline test suite that runs with no network and no API key. It answers the stage's question with a yes: the plug-in point is implementable, and the async-stream shape is natural on the implementing side.

    What is still missing

    Two things, both decisions rather than typing. First, three copies of AgentEvent now disagree about whether an event carries a session id. Second, nothing says what cancelling a turn does — and voice, where the user interrupts constantly, is the one domain that cannot leave that unspecified.

    How we will know this stage is done

    One event shape that all three copies agree on, and a written cancellation rule with a test that holds an adapter to it. Then a TypeScript adapter can be written once instead of twice.

    1. Build the reference adapter ClaudeAgentAdapter implements the same plug-in point in Python over claude-agent-sdk. Done

      What this item actually means

      The adapter's job is translation, and nothing else: SDK messages in, AgentEvent out. Everything vendor-shaped stops at this file. That is why it is the only module allowed to import claude_agent_sdk — that single greppable rule is the dependency-inversion boundary, enforceable by search rather than by good intentions.

      It also taught the plan something about failure. The Agent SDK does not raise on auth or model errors; it returns a ResultMessage with is_error set. An adapter that forwards blindly would report a failed turn as a successful one, and the voice policy above would happily speak an error string aloud.

      What was built

      claude_agent_adapter/adapter.py, 91 lines. submit() yields an assistant_text event per text block, keeps the final ResultMessage, and only then yields terminal — after checking is_error and raising AgentCallFailed if it is set. It opens a fresh SDK session per call, with setting_sources=[] and allowed_tools=[] so it answers with text and cannot read files.

      How to check this yourself

      Read the file and confirm the is_error check still sits before the terminal yield. Confirm too that no module outside adapter.py imports claude_agent_sdk; the moment a second one does, the boundary has leaked and this item is no longer done.

    2. Cover the adapter with offline tests Prove the streaming and failure behavior without a network call or an API key. Done

      What this item actually means

      Tests that need credentials get skipped, and skipped tests protect nothing. Because the adapter depends on query() rather than on a live service, the SDK call can be faked with real AssistantMessage and ResultMessage objects — the same inversion that makes the plug-in point useful in production makes it testable offline.

      What was built

      claude_agent_adapter/tests/test_adapter.py with fakes.py alongside it. Three named behaviors are pinned: text blocks stream out then a terminal event arrives; an errored result raises instead of yielding; and a run that produces no ResultMessage at all raises rather than ending silently.

      How to check this yourself

      cd claude_agent_adapter && ../lancedb_memory/.venv/bin/python tests/test_adapter.py. It reports 4/4 passed today. The venv is needed only because claude-agent-sdk must be importable for the fake message classes; no key is read and no request goes out.

      Where the coverage stops

      These are adapter tests, not contract tests. They hold one implementation to its own behavior; they do not yet hold every implementation to a shared rule. That generalization is Stage 3's contract-test item.

    3. Reconcile the three AgentEvent copies Decide whether an event carries a session id, then make all three definitions agree. In progress

      What this item actually means

      This is the item currently being worked on, and it is the reason nothing downstream has started. Three definitions of the same event have drifted apart, and each one is defensible on its own:

      • TypeScript — contracts.ts: sessionId required, generation: number, five kinds.
      • Python service side — voice_communication/pydantic_models/models.py: session_id: UUID required, five kinds.
      • Python adapter side — claude_agent_adapter/models.py: no session field, two kinds (assistant_text, terminal).

      The adapter's omission is not sloppiness; it is an argument. submit( text, generation ) never receives a session id, so an adapter that emitted one would be inventing data. Either the plug-in point hands the session down, or the event stops carrying it and whoever owns the session attaches it above the boundary. Both are coherent designs. Choosing is the work.

      What exists today

      All three files, all valid, all disagreeing. The disagreement is invisible to every current check: tsc and the Python tests each see only their own side, so nothing fails today. That is exactly why it needs a decision rather than a bug report.

      What is still missing

      A decision, written down in one place. Then: whichever of the three definitions loses gets edited, the two-kind Python copy grows to whatever set of kinds is agreed, and a note in the shared contracts file records why — so the next person does not silently re-add the field.

      How we will know it is done

      The three definitions describe the same event; npm run typecheck and the adapter tests both still pass; and the reason for the choice is written next to the type, not just in this plan.

      The next concrete action

      Answer one question: does an adapter know its session? If yes, add the session parameter to submit() and keep the field. If no, drop sessionId from AgentEvent and let the coordinator stamp it. Everything else in this item follows mechanically from that answer.

    4. Decide where cancellation lives Say what happens to a turn the user talks over, and which interface owns that verb. Not started

      What this item actually means

      In a typed chat box, an abandoned response is a cosmetic problem. In voice it is the whole product: the assistant must stop talking the moment the user starts. So “what does cancellation mean” is not a refinement to add later — it is a load-bearing part of the contract.

      There are three candidate homes, and the choice is a design commitment, not a preference. Cancellation can be implicit in the generation number, with the consumer discarding events from superseded turns. It can be a method on IConversationAgent, making every adapter implement it. Or it can be a separate lifecycle interface, keeping the plug-in point at one method for adapters that genuinely cannot interrupt their backend.

      What exists today

      Nothing, and the silence is the risk. generation exists and hints at the first option, but no file says whether a cancelled turn is expected to stop producing events or merely to be ignored downstream. Two adapters could each be “correct” and behave incompatibly.

      What is still missing

      The written rule, in the plug-in point's own doc comment: after a generation is superseded, what may an adapter still emit, and what must a consumer do with it? Then whichever shape the decision implies — a parameter, a method, or a second interface.

      How we will know it is done

      Stage 5's cancellation test can be written from the doc comment alone, without asking anyone what was intended.

      Why it is not started

      It sits behind the AgentEvent reconciliation, because the same question — how much lifecycle the plug-in point owns — is easier to answer once for both.

  3. Stage 3 — Write the TypeScript adapter Turn ILettaAgentAdapter from a reserved name into a class the browser can actually construct. Not started

    What this stage actually means

    The Python adapter proved the plug-in point is implementable. It cannot be shipped to a browser. This stage produces the implementation that Toyota will actually hold at runtime — the first non-type-only code in this block.

    What exists today

    A name and a promise: interface ILettaAgentAdapter extends IConversationAgent {}, which adds nothing and implements nothing. Every TypeScript file in this package is still type-only, so this stage also introduces the package's first emitted JavaScript.

    What is still missing

    All of it — the class, the stream translation, and the contract tests that keep the next adapter honest.

    Why it is not started

    The translation layer is written against the event shape. Starting before Stage 2's reconciliation lands means writing it, then rewriting it.

    1. Implement the LettaAgentAdapter class A concrete class satisfying IConversationAgent, holding its transport as an injected dependency. Not started

      What this item actually means

      One class with one async generator method. The interesting constraint is what it must not do: it must not construct its own transport, read global configuration, or know that a UI exists. Its dependencies arrive through its constructor so that a test can hand it a fake and a composition root can hand it the real one.

      Follow the Python adapter's shape — it is the reference implementation for a reason, and matching it keeps the two sides of the boundary legible to the same reader.

      What is still missing

      The file itself. letta_agent_adapter/letta_agent_adapter.ts currently holds only the empty extending interface.

      How we will know it is done

      The class compiles under npm run typecheck with an explicit implements IConversationAgent, and it is the only file in this block that names Letta's transport.

      The next concrete action

      Blocked. Start it once Stage 2's event shape is settled — the method signature depends directly on that answer.

    2. Translate the Letta stream into AgentEvent Map vendor messages onto the five kinds, and fail closed on anything unrecognized. Not started

      What this item actually means

      This is where a boundary is usually lost. It is tempting to pass an unmapped vendor message through “just in case” someone downstream finds it useful — and the moment that happens, the voice policy is coupled to Letta's message taxonomy and the plug-in point has become decoration.

      So the rule is: everything is mapped onto one of the five kinds, or it is dropped or raised deliberately. Unknown kinds fail closed. The Python adapter's is_error handling is the pattern to copy — a failed turn must never arrive downstream wearing the shape of a successful one.

      What is still missing

      The mapping table itself, and the decision for each vendor message type: which of the five kinds it becomes, or why it is dropped.

      How we will know it is done

      Every emitted event is one of the five kinds; an unmapped vendor message produces a deliberate outcome rather than a silent pass-through; and a backend failure ends the stream as error or a raised failure, never as terminal.

    3. Write contract tests in TypeScript One suite any adapter must pass, so the second adapter cannot quietly redefine the plug-in point. Not started

      What this item actually means

      Adapter tests and contract tests are different animals. An adapter test checks one implementation's own behavior; a contract test is written against the interface and run against every implementation, so it is the artifact that keeps two adapters honestly interchangeable.

      The critical constraint: the suite must not import anything from Toyota or from any UI. The moment it does, the plug-in point's definition is entangled with a consumer, and a second consumer inherits assumptions nobody wrote down.

      What is still missing

      Everything, including the choice of runner — this package currently has no test tooling at all, only typecheck in its package.json scripts.

      How we will know it is done

      The same suite runs green against the Letta adapter and against a hand-written fake adapter. If it only passes for one of them, it is an adapter test wearing a contract test's name.

  4. Stage 4 — Adopt the plug-in point in Toyota Input Options Make the real screen depend on the interface instead of issuing its own request. Not started

    What this stage actually means

    Until a real consumer depends on it, a plug-in point is a hypothesis. This stage is the first one where an existing, working screen changes — which makes it the first stage that can break something a user would notice.

    The discipline for the whole stage is therefore: behavior identical, dependencies inverted. If the screen behaves differently afterwards, the refactor failed even if the architecture looks better.

    What exists today

    Toyota Input Options lives outside this workspace, in the dashboard application; nothing in agent_blocks imports it, and no adoption work has begun on either side. IToyotaVoiceApplication here is a two-method facade (start, stop) and nothing more.

    What is still missing

    Everything — and one piece of homework first: read how Input Options sends today, including its resume and timeout behavior, and write that down as the behavior the refactor must preserve. Before that reading exists, this stage cannot be estimated honestly.

    Why it is not started

    It requires a shippable TypeScript adapter from Stage 3. There is nothing to inject yet.

    1. Construct the adapter at Toyota's composition root Name the concrete class in exactly one outer place, and pass the plug-in point inward. Not started

      What this item actually means

      Dependency inversion is not achieved by having an interface; it is achieved by where the concrete class is named. Exactly one outer location may say new LettaAgentAdapter( ... ). Everything inward receives an IConversationAgent and cannot tell which implementation it holds.

      This is the same rule the workspace already applies on the Python side, where only main.py names concrete implementations. It is greppable, which is what makes it survive.

      How we will know it is done

      Grepping the adapter's class name in the Toyota application finds exactly one construction site, and the component holding it declares only the interface type.

    2. Replace the direct request call Route the send through submit() without losing resume or timeout behavior. Not started

      What this item actually means

      The screen stops issuing a request and starts consuming a stream: for await ( const event of agent.submit( text, generation ) ). The rendering code moves from “await a response, then draw” to “draw as events arrive”.

      The hazard is the behavior that lives around the old call rather than inside it — resume-after-reconnect, request timeouts, retry. That logic is easy to lose in a refactor because it is not part of the happy path, and it is exactly what users notice when it disappears.

      What is still missing

      A written inventory of the current send path's behavior, produced before the first line is changed. It is the checklist the refactor is graded against.

      How we will know it is done

      Every behavior on that inventory still holds after the change, and the screen no longer imports any transport directly.

    3. Keep input clearing out of the plug-in point Submit an immutable text snapshot; clearing the box stays with Input Draft and the coordinator. Not started

      What this item actually means

      There is a pull, during every adoption like this, to let the agent call clear the text box — both happen on send, so it feels like one action. It is two responsibilities: talking to an agent, and mutating UI state. Joining them means every future adapter, including a headless voice one with no text box at all, inherits a UI concern.

      The plug-in point receives an immutable snapshot of the text. What the input field does next belongs to IInputDraft and the conversation coordinator, which are separate blocks in this package for exactly this reason.

      How we will know it is done

      No adapter and no call into submit() touches input state, and a headless caller can submit a turn without any input component existing.

  5. Stage 5 — Verify one live voice turn Prove one whole path works out loud before adding the remaining Voice Communication blocks. Not started

    What this stage actually means

    One narrow slice, verified end to end, is worth more than four blocks that each look finished in isolation. This stage is the acceptance gate for everything above it: microphone in, agent stream through the plug-in point, speech out.

    What is still missing

    All of it. No implementation of this plug-in point has ever run in a browser, so there is no observation to record yet.

    How we will know this stage is done

    The focused tests pass, and a person has watched one complete turn happen in a real browser for each adapter path that is meant to satisfy the plug-in point.

    1. Run the focused behavior tests Three separately diagnosable checks: vocabulary, ordering, and cancellation. Not started

      What this item actually means

      Split by failure mode, not by convenience. One big “it works” test tells you something broke; three narrow tests tell you what broke, which is the entire value of a test at this boundary.

      How we will know it is done

      Each of the three children below passes on its own and names a distinct defect when it fails.

      1. Test the event vocabularySupported kinds are admitted; unknown kinds fail closed instead of passing through.Not started

        What this item actually means

        The check that keeps the boundary sealed. Feed the adapter a vendor message it has no mapping for and assert that nothing unrecognized reaches the consumer — a passed-through unknown kind is how a plug-in point quietly stops being one.

        How we will know it is done

        Every one of the agreed kinds round-trips, and an unmapped input produces the deliberate outcome chosen in Stage 3 rather than an event the consumer has to guess about.

      2. Test event orderingText arrives before the terminal event, and nothing follows a terminal.Not started

        What this item actually means

        Consumers rely on ordering whether or not it is written down. A voice policy that speaks on assistant_text and closes the turn on terminal is broken by an adapter that emits them out of order — it will cut itself off mid-sentence.

        The Python adapter already behaves correctly here: it holds the ResultMessage aside and yields terminal only after the stream is exhausted. This test generalizes that from one implementation's habit into the plug-in point's rule.

        How we will know it is done

        A terminal or error event is always last, and no event of any kind follows it.

      3. Test cancellationA superseded generation produces nothing the consumer can still act on.Not started

        What this item actually means

        The user talks over the assistant. This test asserts the outcome that Stage 2's cancellation decision defines — which is why it cannot be written yet: there is currently no rule to assert against.

        How we will know it is done

        The test is derivable from the plug-in point's doc comment alone. If writing it requires asking someone what cancellation was supposed to mean, Stage 2's item was never really finished.

    2. Verify the live browser flow One recorded observation per adapter path built on this plug-in point. Not started

      What this item actually means

      Tests are written against what we believed. This item is the check against what actually happens — browser permissions, audio devices, stream buffering, and latency are all things no unit test in this plan will ever exercise.

      How we will know it is done

      Both children below have a recorded observation: what was said, what appeared, what was heard, and how long it took.

      1. Verify the Letta submission pathToyota renders normalized reply events after submitting through the Letta adapter.Not started

        What this item actually means

        The first end-to-end proof: type into the real screen, and watch reply text render from events that came through the plug-in point rather than from a direct response object. This is the moment Stages 3 and 4 are validated together.

        How we will know it is done

        Text streams into the screen as events arrive, the turn ends cleanly on the terminal event, and an induced backend failure shows as an error rather than as an empty successful turn.

      2. Verify the Pipecat voice pathA spoken turn produces the same normalized events, out loud, through the same plug-in point.Not started

        What this item actually means

        This is the point of the whole block: a second, completely different backend satisfies the same interface, and the code above the boundary does not change to accommodate it. Speech in, agent events through the plug-in point, speech out.

        If anything above the boundary needs a special case for the voice path, the plug-in point is wrong — and finding that out here, on one slice, is far cheaper than finding it out after the remaining Voice Communication blocks are built on top of it.

        How we will know it is done

        One spoken turn completes out loud, interrupting the assistant behaves per the cancellation rule, and no consumer-side code branches on which adapter is in use.
