The IConversationAgent

Chapter 1 — A Stable Doorway to Any Agent Backend

1.1 The one idea to understand first

Before thinking about microphones, speech recognition, Pipecat, Letta, or text-to-speech, learn this sentence:

Key Idea IConversationAgent is the small, stable doorway through which Toyota sends text to an agent and receives a stream of normalized events.

Toyota should know what it wants to do—submit a person’s words and observe the resulting conversation—but it should not need to know which vendor, transport, or model produced the answer.

The leading I means “interface.” This Agent Block describes a promise that adapters must keep. It is not itself a chatbot, model, HTTP route, or Pipecat pipeline.

1.2 Think of the interface as a universal doorway

Imagine that Toyota is a university classroom. The professor wants to ask a question, but the guest lecturer may change from week to week. One week the lecturer is Letta. Another week it may be a local model or a test double.

The classroom does not rebuild its doors for every lecturer. Everyone enters through the same doorway and follows the same classroom rules.

University Principle High-level conversation policy should depend on a small interface. Technology-specific adapters should depend on that same interface—not the other way around.

1.3 The complete contract

The TypeScript interface is deliberately small enough to read in one glance:

<> Visual Studio Code—   □   ×
TS   conversation_agent.ts
export interface IConversationAgent {
  submit(
    text: string,
    generation: GenerationId,
  ): AsyncIterable<AgentEvent>;
}

One method is enough because the interface expresses one responsibility: submit a conversational turn and observe its output.

PartPlain-language questionWhy it exists
textWhat did the person say?Carries the completed text turn. It does not carry raw microphone audio.
generationWhich attempt does this work belong to?Lets consumers reject events from an older or cancelled attempt.
AsyncIterableHow do results arrive?Allows multiple events to arrive over time instead of forcing one final response.
AgentEventWhat shape does every result use?Normalizes backend-specific output into a vocabulary Toyota can understand.

1.4 Why the answer is a stream

An agent turn is rarely a single indivisible value. A backend may expose reasoning, tool activity, one or more assistant-text fragments, and then a terminal signal. It may also report an error.

AsyncIterable<AgentEvent> gives Toyota a standard way to receive those events as they happen:

Event kindMeaningTypical consumer behavior
reasoningNon-final working or explanatory output.May be displayed, but should not automatically be spoken.
assistant_textUser-facing answer text.Render it and allow spoken-output policy to consider it.
toolActivity from a tool used during the turn.Show it as status or diagnostic information.
terminalThe generation has reached a normal end.Close the active lifecycle cleanly.
errorThe generation could not complete normally.Stop the lifecycle and present a recoverable error state.
Design Boundary The interface reports what happened. Separate policy decides what appears in the transcript, what may be spoken, and what ends or cancels the turn.

1.5 Generation identifiers prevent time-travel bugs

Voice systems are asynchronous. A user can begin a new capture while an older transcription or agent request is still finishing. Without an identity for each attempt, a late result from the old attempt can overwrite the new one.

The generation value travels into submit() and comes back on every AgentEvent. The coordinator can then apply a simple rule:

<> Conversation lifecycle rulePlain text
TXT   generation-rule.txt
if event.generation !== activeGeneration:
    ignore the event because it belongs to stale work
else:
    apply the event to the current conversation

This matters directly to Toyota’s Input Options page. Pressing the voice control should clear the visible textbox and its backing draft before fresh speech arrives. The UI owns that clearing action. The generation check then prevents an older callback from putting stale text back into the newly cleared field.

Concurrency Principle Clearing the textbox fixes the immediate state. Checking the generation protects that state from late asynchronous results.

1.6 What this Agent Block owns—and what it does not

It ownsIt deliberately does not own
The framework-neutral submit() contract.Microphone capture or browser recording.
The requirement to preserve the generation identity.Speech-to-text and transcript assembly.
The normalized AgentEvent stream returned to policy.Which event kinds are displayed or spoken.
The seam that concrete agent adapters implement.Letta HTTP details, Pipecat internals, or model-provider details.
A boundary that can be replaced by a fake in tests.Session orchestration, interruption, and text-to-speech.

These exclusions are a strength. They allow each neighboring Agent Block—such as the conversation coordinator, speech recognizer, spoken-output policy, and Pipecat service client—to be implemented and tested independently.

1.7 Where Pipecat fits

Pipecat remains a separate local service. It coordinates real-time voice pipeline concerns on the Python side. Toyota remains the composition boundary on the browser/dashboard side.

IConversationAgent is part of that larger system, but it is not the Pipecat client. Its concern begins after usable text exists and ends after normalized agent events are exposed. A coordinator will combine this port with the other voice blocks to form the complete turn.

Mental Model Pipecat helps conduct the voice orchestra. IConversationAgent defines the music stand used to communicate with whichever conversational agent is playing one part.

1.8 Construction status

Current state: design skeleton. The typed interface and shared event contracts exist, and reference diagrams describe the intended boundary. Toyota has not yet adopted this port, and the Pipecat-backed vertical slice is not complete.
