Choosing an Embedder

A plain-language walkthrough of the one open decision left in the memory system: what turns a sentence into the list of numbers LanceDB actually searches over.

What an embedding even is

LanceDB doesn't search text. It searches vectors — fixed-length lists of numbers, like [0.12, -0.87, 0.34, ...]. An embedder is the piece of code that converts a sentence into one of these lists. Two sentences that "mean similar things" should produce two vectors that sit close together in that numeric space. Recall then just means: embed the new message, and ask LanceDB for the closest existing vectors.

Analogy

Think of every message as a dot placed on a map, and the embedder as the rule for choosing where to place it. A good rule puts "I love hiking" and "I enjoy trail running" near each other, and puts "how do taxes work" somewhere far away. A cruder rule might just place dots based on which words are literally shared — still useful, just less clever about meaning.

What's running today: HashingEmbedder

Right now, agent_memory/adapters/hashing_embedder.py does the placing. It's deliberately simple: it looks at the words in a message, hashes each one into a bucket (one of 256 numbers), and adds or subtracts a small amount from that bucket. The result is normalized into a 256-number vector. No network call, no API key, no external model — it's pure arithmetic on the words that are already there.

That makes it lexical: it groups messages that share words, not messages that share meaning. "My car won't start" and "the engine is dead" would not be recognized as related, because they share almost no words. This exists mainly because Anthropic's Claude doesn't offer an embeddings API to pair with the chat model this agent already uses — so HashingEmbedder is the free, always-available placeholder that let the rest of the memory system (LanceDB storage, recall, tests) get built and proven correct first.

The decision: keep it, or swap it

This is the fork in the road. Nothing is broken today — recall works, tests pass. The question is only whether "groups by shared words" is good enough for how you plan to use this agent, or whether you want "groups by meaning."

Running now

Keep HashingEmbedder

cost: $0 · network: none · setup: none

Good fit if you're still testing the plumbing, want zero dependencies, or your conversations tend to reuse the same vocabulary (so shared words are already a decent proxy for shared topic).

Local upgrade

A local semantic model

cost: $0 · network: none · setup: one package install

A small open-weights model (e.g. via the sentence-transformers Python package) runs on your own machine and produces vectors based on meaning, not just word overlap. No API key, but it's a heavier dependency and slower per message than hashing.

Hosted upgrade

A hosted embeddings API

cost: per-call, small · network: required · setup: API key

Services like OpenAI, Voyage, or Cohere offer an embeddings endpoint over the network. Highest quality, but it reintroduces the network dependency and API key management that switching to the Claude SDK was partly meant to reduce.

Not recommended here

Anthropic embeddings

doesn't exist

Worth naming just so it's not a mystery: Claude has no embeddings endpoint today. It's why the agent uses two different providers for two different jobs — Claude for conversation, something else for vectors.

Why this touches LanceDBMemoryStore too

You can't just swap the embedder in isolation. LanceDBMemoryStore (in agent_memory/adapters/lancedb_store.py) creates its table with a fixed vector width — currently 256, matching HashingEmbedder. Every embedder produces a different width: a local semantic model is commonly 384 numbers, a hosted API is often 1536. If the widths don't match, the store raises an error immediately rather than silently writing vectors that can never be searched correctly — that's intentional, not a bug to work around.

Practically, this means a swap is a two-part change: pick the new embedder, and point Settings.table_name in config.py at a new table name so the old 256-wide table is never mixed with new, differently-sized vectors.

1

Decide what you're optimizing for

Zero dependencies and instant setup (stay with hashing), or better recall quality on conversations that rephrase the same idea in different words (move to semantic).

2

Pick the embedder

Stay with HashingEmbedder, or write a new class implementing the same Embedder protocol (one async embed(text) method) backed by a local model or hosted API.

3

Give it a fresh table

Change table_name in config.py so the new vector width gets its own LanceDB table instead of colliding with the old one.

4

Wire it in one place

The swap happens only in main.py's composition root, where the embedder is constructed — nothing else in the codebase should need to change, since agent.py only knows about the Embedder protocol, never the concrete class.

No decision needed yet

There's no wrong choice here right now. HashingEmbedder is a legitimate, working default, not a placeholder that must be replaced. Swap it only once you notice recall missing conversations that clearly should have matched — that's the concrete signal that "shared words" has stopped being good enough, and "shared meaning" is worth the extra dependency.
